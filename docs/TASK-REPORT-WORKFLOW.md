# Assigned Task Reports

A current independent claimant can save a progress Report while its Task is in progress using POST /tasks/{id}/reports, MCP relayhall_task_report_save, CLI task-report, or the Task details Reports & handovers form. The server records the authenticated author and source Task, creates the legitimate Report Reference, and recomputes automatic assignment access. No manual Grant or Warrant is required. A taskIds association on a standalone private Report does not confer this authority.

Editing requires reportId and the last content_hash as expectedContentHash. Reassignment, release, Review and Completed revoke editing; a foreign author's Report cannot be edited. A saved Report is handed over through the existing atomic Task finish interface. Its content cannot subsequently be modified through generic Report PATCH. The Verifier remains independent.

GET /tasks/{id}/reports?scope=progress, MCP relayhall_task_report_list with scope "progress" and CLI task-reports --scope progress list only readable task-bound progress Reports. Without a scope they list every readable Report associated with the Task. Every form returns bounded summaries, never bodies: the five newest by default, pinned evidence separately, the readable total and a nextCursor (CLI --all follows it through every page). A summary of one of the Task's own progress Reports carries its contentHash. The current claimant reads its progress Report in full, body and content_hash, with GET /tasks/{id}/reports/{reportId}, MCP relayhall_task_report_get or CLI task-reports ID --report REPORT_ID. These need Task read authority (tasks:read), not reports:read, and serve only progress Reports of that Task the caller may read. Read any other Report's body with GET /reports/{id}, MCP relayhall_report_get or CLI report get, which need reports:read. See [Task Report context](api.md#task-report-context). Current Task assignee, Shepherd and Verifier receive READ of server-bound workflow Reports through the shared authorization predicate. Human assignment-chain access is provided by the existing assignment vehicle and legitimate reference cap; this does not expose unrelated private acceptance/native Reports.

## Who the claimant is

The claimant that maintains a Task's progress Report is the Task's current Assignee: `tasks.owner_principal_id`, which `task_assignments.claimant_principal_id` mirrors. A human Account is a claimant in exactly the way a Connector is; there is no separate rule for the creator. Creating a Task does not assign it: the creator becomes its Shepherd, not its Assignee. An Account becomes the Assignee by claiming the Task with POST /tasks/{id}/claim, MCP relayhall_task_claim, or Claim Task on the Task details page. Task write access, the Shepherd role and Account ownership do not make an Account the claimant, and the Task's Verifier can never become it.

The one supported dashboard path to a progress Report is: Arm the Task, Claim Task, set Status to In progress, then save in Reports & handovers. Until the Task is In progress, the Assignee's `reportMaintenanceAccess` answers `TASK_REPORT_FROZEN` and every other caller's answers `TASK_CLAIMANT_REQUIRED`; the Reports & handovers section names the remaining step from those two decisions and the caller's `lifecycleAccess.claim`. Save, reload and restore of a draft then behave for a human Assignee exactly as for any claimant.

A claim that answers 200 always means the caller is the Assignee, and `claim.outcome` says how: `claimed` when this call assigned it, `already_assignee` for the accepted retry, which changes nothing. A refusal is never a 200. It keeps its status and code and carries `details.reason` in the vocabulary of `lifecycleAccess.claim.reason`: `TASK_ALREADY_ASSIGNED`, `INDEPENDENT_VERIFIER`, `TASK_NOT_ARMED` and `TASK_BLOCKED`, plus `TASK_CLAIM_AUTHORITY_CHANGED` and `TASK_ASSIGNMENT_EPOCH_MISMATCH` for the two refusals that only the claim itself can decide. A claim that assigns writes one `task.claim` audit row with outcome Succeeded and the `task.claimed` entry on the Task timeline, in the claim's own transaction. Every refusal the claim route decides writes one `task.claim` row with outcome Refused and its reason, never the identity that holds the Task. A caller with no claim authority at all is refused 403 by shared authorization before the claim route runs, as for every Task write, and that refusal is not a `task.claim` row. The dashboard disables Claim Task whenever `lifecycleAccess.claim.allowed` is false and shows the reason beside it, and it announces every claim outcome as a toast.

MCP saves require a unique idempotencyKey. A repeated committed act is refused rather than replayed past assignment revocation: 409 IDEMPOTENCY_REPLAY_UNAVAILABLE, whose message names the exact recovery route GET /tasks/{id}/report-operations/{key}?requestHash=... with this save's request hash filled in (MCP relayhall_task_report_reconcile), and never the Agent mint text. If the create outcome is uncertain, read the Task Reports and reconcile the exact known result; do not blindly create again. No new native execution/generation protocol is introduced.

Validation uses focused transaction, authorization, MCP, CLI and UI tests. SQL transaction tests use controlled storage; these are not a real PostgreSQL concurrency or deployed qualification claim.


## Bounded Task read

GET /tasks/{id} computes reportMaintenanceAccess under the Task row lock a save takes, and waits for it at most 2 s. A transaction that holds the Task longer refuses the read with 409 TASK_READ_BUSY and Retry-After: 1; nothing is read or changed. MCP relayhall_task_get composes the same route and carries the same bound. Native review evidence share-locks dependency Tasks without waiting: a refusal caused by such a read is retried once after 250 ms, and a second refusal answers 409 NATIVE_REVIEW_EVIDENCE_BUSY.

## Correction: logical save recovery and evidence audience

Every public Task Report save requires one logical Idempotency-Key. The Task lock transaction stores the exact author/task/key/request hash and committed Report hash alongside the Report and genuine reference. A middleware receipt failure cannot create a second Report on a same-key takeover. REST GET /tasks/:id/report-operations/:key?requestHash=... and MCP task_report_reconcile read only the exact mapping after fresh current claimant and access checks; changed Report hashes refuse. CLI --idempotency-key is required; --reconcile reads first. The browser retains the pending operation in sessionStorage scoped to deployment, authenticated author and Task across navigation/reload, clears it only after exact reconciliation, and uses the same key after an authenticated unknown result. A permission refusal never proves an earlier ambiguous save did not commit.

Report READ is also derived from an existing genuine typed Report reference created by that Report's canonical authenticated author UUID. Association arrays alone grant nothing. Current Task creator/owner/Shepherd/Verifier and the active parentless human reached by their valid, noncyclic, credential-live chain may read evidence even after Task completion. This is READ only, calculated from current roles and references at every query: reassignment, unlink, inactive/expired/revoked/cyclic chains remove the derived audience. Native verdict/execution outputs and foreign-author references are excluded. No grants, Report content, origin, or task WRITE authority are rewritten.

Saved Task-report handoff verifies immutable Task/author/origin and a matching transactional operation mapping, then refreshes Task WRITE scopes, presented credential and explicit delegated object caps after the Task lock before effects. Genuine saved-report handoff requires current authenticated authority. This scoped path leaves generic legacy API/inline Report finish behavior unchanged. READ-only operation reconciliation remains independently permitted.
